# M1 Engine Benchmark Report — libVLC vs mpv

**Date:** 2026-10-27 · **Machine:** one Windows 11 laptop (i7-8565U, Intel UHD 620 display GPU,
NVIDIA MX150 idle, 3840×2160 @ 60 Hz, on AC, *Balanced* plan) — full details in the
[environment report](environment-report.md).
**Engines:** libVLC 3.0.24 x64 (official VideoLAN zip) · libmpv v0.41.0-1227-ge471496c5
(shinchiro build 20261021). **Bindings:** python-vlc 3.0.21203 · python-mpv 1.0.8.

All numbers below come from tool output in this repository; nothing was estimated or
filled in by hand. Raw per-trial data: `tools/engine-benchmark/results/raw/run-20261027-041422.json`
(git-ignored); committed summary: [`results/summary.md`](../../../tools/engine-benchmark/results/summary.md)
and `summary.json`.

## 1. Method

- Both engines are driven through the **same `PlaybackEngine` adapters** the app uses,
  rendering into a real 1280×720 Qt window (window-handle embedding).
- **5 trials** per engine × media, each in a **fresh process** (includes DLL load and
  engine start). Engine order alternates per trial.
- Media: synthetic clips generated by `make_media.py` (FFmpeg `testsrc2` + −60 dB sine;
  commands and SHA-256 in `media-manifest.json`): H.264 1080p30, HEVC 2160p30, VP9
  1080p30, AV1 1080p30, a 720p file with 2 audio + 2 subtitle tracks, and two invalid files.
- Per perf trial: engine init, open → playback progress, 8 s steady playback (process
  CPU, RSS, dropped frames), three seeks (25/50/75 %), close time, hardware decoder and
  video output reported by the engine, rejected state transitions.
- Comparable timing metrics are **progress-based** (time until the reported position is
  500 ms past the open/seek target, minus 500 ms). The engines' own "playing"/"position"
  reports are not comparable: libVLC fires *Playing* before the first frame and reports
  a seek target immediately (0 ms), so those are shown for reference only.
- Targets: none were fixed in advance for M1 (the plan forbids inventing thresholds).
  This run is the baseline that M4 targets should be set from.

### Observations

- **Start-up to real playback** is similar (≈ 0.6–0.85 s) on hardware-decoded media.
  Most of it is common to both (window, D3D11 device, audio output). mpv initialises
  ~0.4 s faster per process.
- **Seek→resume:** mpv is faster on H.264 (103 vs 386 ms) and VP9 (43 vs 279 ms); similar
  on HEVC/AV1. Ranges are wide for both; bounded by each engine's position-report interval.
- **CPU:** comparable (8–12 % of one core on hardware-decoded media); AV1 software
  decoding costs ~31–32 % of one core on both.
- **Memory:** libVLC uses about **2× the RAM on 4K HEVC** (924 vs 468 MB).
- **Dropped frames:** mpv drops frames on 4K HEVC on this iGPU; libVLC dropped none.
  Follow-up (`mpv_vo_check.py`, 3 runs each): all drops are **video-output** drops,
  **0 decoder drops**. `vo=gpu-next`: 27/24/27 per 8 s; `vo=gpu`: 10/9/8 per 8 s. So it is
  mpv's renderer cost at 4K on a UHD 620, reducible but not removed by `vo=gpu`.
  Note the counters are not identical in definition (libVLC "lost pictures" vs mpv
  "frame-drop-count + decoder-frame-drop-count").

## 3. Hardware decoding

Both engines used **D3D11VA on the Intel UHD 620** for H.264, HEVC and VP9. Both decoded
**AV1 in software** (the UHD 620 has no AV1 decoder): libVLC logged no hardware decoder,
mpv reported `hwdec-current = no`. Neither used the NVIDIA MX150. libVLC exposes the active
decoder only in its log (parsed by the adapter); mpv exposes it as a property.

## 4. Tracks, errors and recovery

| Check | libVLC | mpv |
|---|---|---|
| 2 audio + 2 subtitle tracks listed | ✅ codecs aac/ac3, subrip/ass | ✅ with languages eng/fra |
| Text file named `.mp4` | ✅ `MEDIA_OPEN_FAILED` in 28–33 ms — **only via adapter heuristic** | ✅ `MEDIA_OPEN_FAILED` in 20–56 ms |
| Truncated MP4 | ✅ same heuristic, 20–25 ms | ✅ 10–16 ms (`avformat_open_input() failed`) |
| Plays a valid file afterwards | ✅ 3/3 | ✅ 3/3 |
| State sequence on bad file | LOADING → PLAYING → ERROR | LOADING → ERROR |

libVLC on its own reports an unreadable file as *Playing → EndReached* with **no error
event** (it falls back to the MPEG-PS demuxer "continuing anyway"). The adapter treats
"ended with position 0 and nothing decoded" as an open failure; the UI still sees a
brief PLAYING.

## 5. Repeated use and memory

| Check (benchmark `cycles` scenario) | libVLC | mpv |
|---|---|---|
| 15 open/play/stop cycles, failures | 0 | 0 |
| RSS first → last cycle | 270 → 358 MB | 240 → 334 MB |
| 5 engine create/close cycles, RSS first → last | 331 → 335 MB | 318 → 316 MB |
| Threads first → last | 15 → 14 / 11 → 11 | 23 → 23 / 9 → 8 |
| **Process exit** | clean (exit 0) | **access violation 0xC0000005** |

RSS growth over 15 open/stop cycles is similar for both and may be caches warming up;
15 cycles is too short to call it a leak. Create/close cycles are flat. **Inconclusive —
long-session tests belong to M4.**

## 6. Stability findings (most important for the decision)

| # | Finding | Engine | Evidence | Status |
|---|---|---|---|---|
| S1 | **Access violation (0xC0000005)** when a process has created and closed more than one mpv instance via the adapter: at process exit, and once mid-run. | mpv | Benchmark cycles 2/2 runs; targeted repeat 8/8; mpv integration suite, exit code checked: 4/4 processes (3 at exit after 7/7 tests passed, 1 during the first test), plus one more mid-run crash in an earlier loop; `mpv_vo_check.py` 1/1. Single-instance processes exit cleanly (40/40 perf, 6/6 errors/tracks). A minimal python-mpv script with the same options did **not** crash (25/25). | **Open — root cause not isolated** (python-mpv 1.0.8 teardown vs this libmpv build vs adapter usage). Blocks selecting mpv until resolved. |
| S2 | **Deadlock** when the Qt host window is destroyed while libVLC still renders into it: GUI thread holds the GIL in `DestroyWindow`, libVLC's Direct3D11 window thread waits for the GIL inside the Python log callback. | libVLC (pattern applies to any engine calling Python from its own threads) | py-spy native stack dump of a hung test process. Before fix: 3 of 4 integration runs hung. After fix (close engine first; detach log callback first in `close()`): 10/10 runs, 7/7 tests, exit 0. | **Fixed in tests/adapter; rule recorded** in architecture overview. An earlier one-off hang in the benchmark `tracks` scenario (1 of 21 runs, before the S3 fix, not captured) may be the same class; unconfirmed. |
| S3 | Teardown race: a deferred media-info call could run against a released engine handle. | both (adapter bug) | Stack traces from mpv runs. | **Fixed** — `EngineBase.close()` drains the worker before adapter teardown. |
| S4 | python-vlc `Media.tracks_get()` crashes the process (access violation). | libVLC binding | Reproduced on first call. | **Worked around** with a minimal ctypes struct. |

## 7. Integration effort (from building the two prototypes)

| Topic | libVLC (python-vlc) | mpv (python-mpv) |
|---|---|---|
| Active HW decoder | log parsing only | `hwdec-current` property |
| Errors on bad files | none — needs heuristic | precise `end-file` error with reason |
| Position after seek while paused | **no event** — adapter reports target itself | `time-pos` updates |
| Track info | binding crash (S4) → own ctypes | `track-list` property |
| Callback threads | **engine threads call into Python** (events + log) → GIL hazards (S2) | python-mpv pulls events on its own Python thread; mpv threads never call Python |
| Seek after end | not implemented in prototype (needs restart logic) | works (`keep-open`) |
| Process stability | clean after S2 fix | S1 open |
| Plugins / modules | 360 DLLs, trimmable by deleting files | one static 121 MB DLL — trimming requires rebuilding |

## 8. What this benchmark does **not** show

- One machine, one Intel iGPU, Windows 11 only, one display (4K). No AMD/NVIDIA
  display GPU, no Windows 10, no HDR, no 10-bit HEVC, no interlaced/odd containers.
- Warm OS file cache throughout; true cold start not measured.
- GPU utilisation and power were not measured; CPU is per-process only.
- Seek/open timings are progress-based estimates, not photon-on-screen measurements.
- Long sessions (hours), sleep/resume, display changes and audio device changes were not tested.
- Two small libVLC adapter changes were made **after** the final benchmark run (report the
  target position when seeking while paused; detach the log callback first in `close()`).
  Neither affects the measured perf paths (seeks were measured while playing); close
  time may differ marginally. Integration tests were run on the final code.
