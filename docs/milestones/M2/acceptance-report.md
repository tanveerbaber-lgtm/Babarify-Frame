## Resource stability (pre-set thresholds)

Thresholds fixed before the first run: after warm-up, RSS growth ≤ 64 MB, thread growth
≤ 4, handle growth ≤ 300 (`tests/stress/test_resource_stability.py`).

| Scenario | Warm-up | RSS growth | Threads | Handles | Result |
|---|---|---|---|---|---|
| 60 opens on one engine, all 24 corpus files, seeks and stops mixed in | 10 opens | −6.9 MB | −18 | −178 | **PASS** |
| 15 engine create → open → close cycles | 3 cycles | +40.4 MB | 0 | +192 | **PASS** (watch) |

The create/close scenario trends upward (~3.4 MB and ~16 handles per engine lifetime).
The app creates one engine per session, so this is not critical, but M4's long-session
tests should confirm whether it plateaus.

## Engine adapter changes in M2 (libVLC)

| Problem found | Fix |
|---|---|
| libVLC fires *Playing* before it knows a file is readable (brief PLAYING before errors) | Hold LOADING until confirmed by length, position > 0 or a video output |
| Ended player ignores `play()`; seeking after end impossible | Restart with `stop()` + `play()`; seek-after-end then pauses at the target |
| MPEG-TS/PS and Ogg report streams and video size after *Playing* | Refresh media info on stream-added and video-output events, then retry while the size is still unknown |
| Raw fourccs (`mp4v`, `VP80`, `WMA2`, …) | Mapped to FFmpeg names, same vocabulary as mpv |
| Video size / fps / language unavailable early | Read from libVLC's track struct via own ctypes definitions |
| Mouse/keyboard captured by libVLC's video window | `video_set_mouse_input(False)`, `video_set_key_input(False)` |
| Log level leaked into error text ("4 Could not open…") | Prefix stripped |

## Issues found during M2 and how they were handled

1. **Privacy: an evidence screenshot captured another application.** The first capture
   grabbed screen pixels while another window (a video in a different player) covered
   the app. The file was deleted before any commit. The capture tool now keeps the
   window on top, raises it, and refuses to save unless Windows reports that every
   sampled point belongs to the Babarify Frame window. All four committed screenshots
   were inspected.
2. Dark standard icons were nearly invisible on the dark control bar → icons drawn from
   the Windows icon font (Segoe Fluent Icons / MDL2) in the theme colour.
3. Status bar showed "decoder: none reported" because libVLC logs the decoder after
   *Playing* → status refreshed once per second while playing.
4. A synchronous open failure was overwritten by the file title → window updated before
   opening, so the error always wins.

## Known limitations (not M2 scope unless stated)

- **mpv (alternate engine):** crash S1 unchanged; its tests are opt-in.
- **UI is functional, not premium** (M3): no auto-hiding controls in fullscreen, no
  playback-speed control in the UI (the engine API supports it), no preferences persistence.
- **No track or subtitle selection UI** (M5); tracks are detected and listed internally.
- **No resume/history/playlists** (M6). Opening a folder is not supported.
- **Network streams are rejected by design** until M8.
- **One machine, one GPU**; tested at one DPI (4K, high scaling) on Windows 11 only.
- No hands-on test by a person yet: controls were exercised by automated tests and
  scripted screenshots. **Recommended:** the owner plays a few personal files before accepting.
- libVLC reports the hardware decoder only through its log; the status bar text depends on it.
- Engine create/close trend (see stress table) to be re-checked in M4.
